# ADR-023 — One Node app serves the web client and the API

**Status:** Accepted (2026-09-22, Stage 6)
**Amends:** ADR-013 (polling, connection and memory budgets) and ADR-015 (job runner modes). Both stand;
this records how they apply when a single process carries all three roles.
**Driven by:** DEPLOY-001, and by the state Stage 5 left production in.

## Context

Stage 5 ended with the API live at `hmedicare.hakeemify.com` and **no way to log in**. The domain's
generated `.htaccess` carries `PassengerBaseURI /`, so every URL on it reaches `apps/api`; the root path
answered:

```json
{ "code": "RESOURCE_NOT_FOUND", "message": "RESOURCE_NOT_FOUND" }
```

The React client was built on the server — `current/nodejs/apps/web/dist/` held `index.html` and
`assets/` — and nothing served it. `CORS_ALLOWED_ORIGINS` was still its default `http://localhost:5173`,
so even a client hosted elsewhere could not have called the API from a browser.

The hosting plan allows ten Node applications, but each is bound to one domain, and the owner has one
domain for this product. Three applications (api, worker, web) would need three domains or subdomains and
three sets of environment variables, each with its own copy of the signing keys and the database URL.

## Decision

One Node application on the domain, carrying three roles:

| Path | Served by |
|---|---|
| `/` and any client-routed path | the built web client (`WEB_DIST_DIR`), with the SPA shell as the fallback |
| `/assets/*` | the client's fingerprinted bundles, cached `immutable` for a year |
| `/api/v1/*` | the API, unchanged |
| `/health/*` | liveness and readiness, unchanged |
| `/internal/*` | token-guarded, unchanged |

The job runner is embedded (`JOB_RUNNER_MODE=embedded`, ADR-015 mode 1+3): the same process runs the loop
behind the singleton lock, and the one-minute cron kick keeps it warm and runs a bounded batch
(`JOB_CRON_BATCH_MAX`, `JOB_CRON_TIME_BUDGET_SECONDS`). Nothing about the runner changes here; it simply
has no separate process to live in.

### Same-origin authentication

The client is served by the app it calls, so its requests are same-origin and **no CORS applies to it at
all**. This is the point of the arrangement rather than a side effect: there is no preflight to
misconfigure and no origin list to keep in step with reality. CSRF protection is unchanged and still
required — same-origin is exactly the condition under which CSRF matters.

A development origin (`localhost`, `127.0.0.1`, `[::1]`) in `CORS_ALLOWED_ORIGINS` is now refused in
staging and production. It grants a real browser nothing and obscures which origins are genuinely allowed.

### One budget

ADR-013's budgets were written per application. With one process they are one budget:

- **Connections.** One pool, sized for API traffic and the embedded runner together, still inside the
  plan's 100 connections per user (HOST-001).
- **Memory.** One `NODE_OPTIONS=--max-old-space-size`, covering request handling, the job batch and the
  static file cache. The client's assets are served from disk, not held in memory; only `index.html` is
  read once at startup.

### Splitting later is configuration

Unset `WEB_DIST_DIR`, set `CORS_ALLOWED_ORIGINS` to the client's new origin, and build the client with
`VITE_API_BASE_URL` pointing back at the API. `apiBase()` already treats an empty value as same-origin and
falls back to `http://localhost:3000` only in a development build. No code changes.

## Alternatives considered

**LiteSpeed serves the static files directly.** Faster, and Node would never see an asset request. Rejected
because the web root under `current/` is generated by the platform and replaced on every deploy, so the
rewrite rules for the SPA fallback would have to be re-applied by hand each time — the same class of manual
step that D-01 turned into an outage.

**A second Node app for the client.** Costs a domain and duplicates the environment, including the signing
keys. It buys independent deploys, which matters when web and API are released separately; they are not.

**A hand-written static handler, to avoid a dependency.** Rejected. Static file serving is where path
traversal lives, and `@fastify/static` (MIT, Fastify org) is far better tested than anything written here
would be. It is pinned in `TECHNOLOGY-STACK.md` and passes the licence scan.

## Consequences

- A slow client request and an API request now contend for the same event loop. Static reads are file
  streams and cheap, but a large asset bundle is worth watching.
- The client and API version together. `/health/live` reports one version, which is now the truth for both.
- The SPA fallback must never answer for an API path, or a mistyped endpoint returns a login page with
  status 200 and the caller parses HTML as JSON. It is keyed on the 404 the API produces, restricted to
  `GET`/`HEAD` requests that asked for `text/html`, and excludes `/api`, `/health` and `/internal`
  explicitly. `apps/api/test/integration/single-app-profile.test.ts` asserts all of it, including that a
  missing asset 404s rather than returning the shell, and that traversal out of the build directory fails.
