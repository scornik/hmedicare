# Final Technical Teardown

## Executive finding
There is no single repository that supplies the target product. The evidence supports a hybrid architectural study, followed by a new implementation. No reference should be forked as the product base without source completion, license review, security review, and a Bangladesh domain redesign.

## Answers to the requested questions
1. **Strongest patient/EHR architecture:** OpenEMR for mature breadth and integrated clinical/practice-management depth; TPT Doctor for a cleaner modern tenant-scoped schema. OpenEMR’s `patient_data`, `users`, `facility`, scheduling, clinical, drug, prescription, document, audit, API, and EHI export surfaces are extensive. TPT’s `Tenant`, `User`, `StaffMember`, `Patient`, `Appointment`, `Encounter`, `DiagnosisCode`, `MedicalCondition`, `PatientMedication`, `Prescription`, `LabOrder`, `Document`, `Notification`, and `AuditLogEntry` boundaries are easier to isolate conceptually.
2. **Strongest telemedicine architecture:** HCW@Home. `ConsultationStatus`, `Participant`, invitation tokens, messages/read receipts, media permissions/events, and explicit mediasoup server/router/transport/producer/consumer models provide the clearest call architecture.
3. **Strongest AI/voice workflow:** None verified. DocPilot has no AI/backend evidence; TPT has decision-support entities but no proven LLM/voice pipeline; HCW has no verified AI implementation.
4. **Strongest mobile architecture:** Medigo for a complete patient/doctor split with Firebase-backed mobile workflows and Agora calls; DocPilot for a cleaner shared Flutter package structure. Medigo is materially older and carries stronger security/maintainability concerns.
5. **Strongest prescription workflow:** TPT Doctor by model coverage: `Prescription`, `Drug`, `PatientMedication`, `DrugInteraction`, controlled-substance/e-prescribing and regional prescription entities. A working editor/PDF/delivery workflow was not proven.
6. **Components to study:** OpenEMR’s mature relational clinical/EHI model, FHIR/REST and audit surfaces; TPT tenant and clinical boundaries plus audit/consent/encryption packages; HCW consultation/media state machine and invitation/message/reminder concepts; Medigo’s patient/doctor mobile split, Firestore booking/chat flow, and Agora integration as patterns only; TPT document/version/checksum/storage-key pattern; DocPilot shared mobile package pattern.
7. **Components to avoid:** Medigo’s legacy dependencies, direct client-side PHI writes, hard-coded Agora configuration, and free-text clinical artifacts; unverified code from unavailable repositories; GPL OpenEMR code unless legal review approves the distribution/service model; HCW’s shared User-as-patient/doctor approach for a longitudinal EHR; generic international billing/claims breadth before Bangladesh needs are known; silent AI writes; treating provider declarations as finished integrations.
8. **Fork anything?** No recommendation to fork. TPT and DocPilot are MIT but still require dependency/asset and security review; OpenEMR is GPL-3.0-or-later and requires legal analysis; Medigo/HCW rights remain unresolved.
9. **Build from scratch?** Build the Bangladesh serial/queue, patient identity, prescription, follow-up, localization, offline delivery, and AI approval workflow from scratch while using the references as patterns.
10. **Hybrid architecture?** Yes: a new Bangladesh domain model and API, TPT-like tenant/EHR separation, HCW-like consultation/media orchestration, DocPilot-like mobile packaging, and provider abstractions for WhatsApp/SMS/email.
11. **Data models to influence design:** OpenEMR’s patient/scheduling/clinical/drug/prescription/document/audit separation; TPT’s `Patient`/`StaffMember`/`Tenant`/`Encounter`; HCW’s `Consultation`/`Participant`/`ConsultationInvitation`/media entities; Medigo’s `Appointment`/`Doctor`/`MedicalReport`/`Prescription` collection boundaries only. Add explicit `Serial`, `LabReport`, `LabResult`, `PrescriptionItem`, `FollowUp`, `CommunicationDelivery`, and AI draft/approval entities because the references do not supply them together.
12. **Do not copy:** source from unknown-license repositories; OpenEMR source without GPL legal analysis; generic international integration entities without a local use case; any code that has not passed authorization/PHI review; AI behavior that writes diagnoses or prescriptions without doctor approval.

## Recommended next technical investigation
Before implementation, obtain the missing Medigo submodule sources, run a complete dependency SBOM/license report, verify OpenEMR/TPT/HCW endpoint and authorization tests, and write a Bangladesh domain specification for serials, patient identity, medicine catalog, prescription rendering, delivery receipts, follow-up, offline sync, and AI draft approval.

## Confidence and blockers
Confidence is high for checked-out HCW/TPT schemas, OpenEMR git-object source/metadata, and the separately fetched Medigo submodules; moderate for package-level capability claims, and low for runtime behavior because the references were not built or exercised in this teardown. The original `reference-repos/Medigo` checkout remains unmodified; Medigo source was analyzed from `medigo-analysis/` at the parent-pinned commits.

No overall winner is assigned. The repositories are useful for different architectural lessons, and none is a complete or verified fit for the target workflow.
